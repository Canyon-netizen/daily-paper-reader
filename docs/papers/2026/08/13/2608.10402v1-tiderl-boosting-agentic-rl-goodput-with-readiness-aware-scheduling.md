## 摘要
面向大语言模型的强化学习（RL）正朝着多轮智能体工作负载的方向发展，其中 rollout 任务会反复暂停以等待外部环境，随后在不断增长的上下文中恢复执行，并在高度可变的时间点结束。在这一场景下，RL 训练的有效吞吐量（以训练吞吐量为衡量）比原始 GPU 占用率更为重要：GPU 等待与重复的 prefill 重计算都属于纯粹的额外开销。我们提出 TideRL，一个具备就绪感知能力的弹性 RL 系统，包含持续任务批处理（CTB）、资源感知的 Ref-Actor 流水线（RA²P）以及弹性资源伸缩（ERS）。CTB 保留有用的 rollout 状态；RA²P 根据就绪积压与到达间隔，在解耦流式与同置聚合之间进行选择；ERS 则利用相同的就绪信号，在 rollout 与训练之间迁移资源等级。在纯文本与多模态智能体工作负载上的实验表明，TideRL 将 RL 训练有效吞吐量相对同步基线最高提升 5.6 倍，相对异步基线提升超过 33%，同时达到相近的任务性能。它还将 KV 缓存命中率提升 1.58 倍，每步训练时间最高减少 44.3%，总等待时间最高削减 77.6%。

## Abstract
Reinforcement learning (RL) for large language models is moving toward multi-turn agentic workloads, where rollout tasks repeatedly pause for external environments, resume with growing contexts, and finish at highly variable times. In this setting, RL training goodput, measured by training throughput, matters more than raw GPU occupancy: GPU waiting and repeated prefill recomputation are pure overhead. We present TideRL, a readiness-aware elastic RL system with Continuous Task Batching, Resource-Aware Ref-Actor Pipelining, and Elastic Resource Scaling. CTB preserves useful rollout state, $\textrm{RA}^2\textrm{P}$ selects between decoupled streaming and colocated aggregation from the ready backlog and arrival interval, and ERS moves ranks between rollout and training using the same readiness signals. Across text-only and multi-modal agentic workloads, TideRL improves RL training goodput by up to 5.6$\times$ over synchronous baselines and over 33% over asynchronous baselines, while reaching similar task performance. It also improves KV cache hit rate by 1.58$\times$, reduces per-step training time by up to 44.3%, and cuts total waiting time by up to 77.6%.

## 2. 方法论

### 整体架构
TideRL 是一个**就绪感知 + 弹性异步**的分布式 RL 系统，由三个协同组件构成：
- **CTB（Continuous Task Batching）**：将调度粒度从"请求级"提升到"任务级"。
- **RA²P（Resource-Aware Ref-Actor Pipelining）**：在 Trainer 侧按数据就绪度切换两种 Ref-Actor 执行模式。
- **ERS（Elastic Resource Scaling）**：依据同一组就绪信号在 Rollout 与 Trainer 之间迁移 DP rank。

三者由一条**反馈回路**串联：CTB 控制就绪时刻，RA²P 暴露当前就绪流的消费成本，ERS 迁移 rank 以消除主导等待。

### Continuous Task Batching (CTB)
- **令牌级准入控制**：将每个 DP rank 视为 token 预算池，通过"轻量探测任务"估计初始足迹，仅当剩余容量容纳该足迹时接纳任务，并在每轮交互后更新实际占用。
- **三层准入约束**：
  - 环境并发上限；
  - 策略陈旧度（staleness）约束；
  - 任务多样性（避免同类任务扎堆造成环境侧 stragglers）。
- **语义感知抢占/恢复**：按优先级评分
$$P(t)=\omega_1\cdot I_{\text{eval}}+\omega_2\cdot G_{\text{completion}}+\omega_3\cdot I_{\text{active}}+\omega_4\cdot L_{\text{context}}$$
  - 优先级层级（从高到低）：评估任务 > 接近完成的 GRPO 组 > 活跃执行中任务 > 长上下文任务。
- **工作亲和性恢复**：恢复暂停任务时优先放回可能保留共享前缀的 rank，避免不必要的 prefix 重算。

### Resource-Aware Ref-Actor Pipelining (RA²P)
- **两个就绪信号**：
  - **RAS（Ready-at-Start）**：训练步开始时已就绪的 micro-batch 数。
  - **TPRM（Time Per Ready Micro-batch）**：后续 micro-batch 到达间隔。
- **两种执行模式**：
  - **解耦流式（Decoupled Streaming）**：Ref 与 Actor 部署在不同 GPU，通过重构计算图把 Actor 的 loss（含 KL 惩罚）推迟到 backward pass，从而让 Ref forward、Actor forward、Actor backward 三者流水重叠，**零模型切换开销**。
  - **共置聚合（Optimized Colocated）**：Ref 与 Actor 共用 GPU，使用：
    1. **就绪批次聚合（Ready-Batch Aggregation）**：将连续到达的 micro-batch 合并为同一组（R₂,₃→A₂,₃），摊销切换开销；
    2. **零拷贝传输**：通过 GPU 共享内存传递序列与 ref_log_probs，绕过网络序列化与冗余内存分配。
- **模式选择成本模型（附录 A）**：
  - 解耦模式总延迟近似为
$$C_{\text{dec}}\approx\sum_{i=0}^{M-1}(i\cdot t_{\text{ref}})+\sum_{i=1}^{N}\max(\delta_i,\, t_{\text{act\_f}}+t_{\text{act\_b}})$$
  - 共置模式总延迟 $C_{\text{col}}$ 由调度器算法逐步模拟得到。
- **Micro-batch 调度**：
  - 共置模式采用"最长处理时间优先 + 之字形分配"，均衡各 rank 计算负载；
  - 解耦模式按"末批最小化"原则排序，缩尾延迟。

### Elastic Resource Scaling (ERS)
- **就绪计划生成**：监控生成赤字（global batch 体积 $<B_{\text{ideal}}$）与消费赤字（队列头等待时延 $\tau\times T_{\text{step}}$ 或 RAS 突破解耦模式盈亏平衡点）。
- **决策规则**：
  - **生成赤字**：选共置 RA²P，把原本用于解耦 Ref 的 GPU 归还给 Rollout，直接降低 TWT。
  - **消费赤字**：选解耦 RA²P，从 Rollout 回收一个 rank 组建专用 Ref rank，降低 RWT。
- **无缝扩缩**：
  - **缓存无关的任务迁移**：借力 on-policy RL 每个 sync 边界必须清空 KV 缓存的天然属性，CTB 自动把任务迁移到其他活跃 rank，无需物理 KV 传输。
  - **延迟隐藏角色切换**：把 PCIe 权重交换重叠进 `sync_params` 广播窗口，扩缩过程不阻塞训练主循环。
- **边界条件处理**：
  - **抢占式生成分配**（冷启动/评估阶段）：最大化 Rollout 组规模以快速填充 buffer；
  - **自适应数据保留**（Rollout 缩容后）：Trainer 向 $B_{\min}$ 收缩并保留 micro-batch 储池，避免饥饿循环。

## 3. 实验设计

### 工作负载与任务
- **纯文本任务**：WebShop、AlfWorld（最大 20 轮，上下文 ≤8192 token）。
- **多模态任务**：OSWorld、ScienceBoard（最大 50 轮，含滑动窗口图像裁剪，每条轨迹 5–15 张图，分辨率 1280×720）。

### 模型
- 文本：Qwen-2.5-7B、Qwen-2.5-14B；
- 多模态：Qwen-3-VL-4B、Qwen-3.5-9B（含线性注意力与多 token 预测）。

### 对比基线
- **VeRL**：同步 RL 框架，作为同步基线。
- **AReaL**：异步 RL 框架，使用 active partial rollout。
- **StreamRL**：当前 SOTA 异步流式 RL 框架。
- 公平性控制：所有框架使用相同 GPU 预算、任务流、checkpoint、staleness 上界、global batch 与 rollout/training backend；固定分区基线在 $\{$0.125, 0.25, 0.5, …$\}$ 比例中取最佳者。

### 评估指标
- **主要指标**：训练吞吐量（被 Trainer 消费的 token/秒）。
- **次要指标**：BoN 奖励、pass rate、KV cache 命中率、生成吞吐量、RWT、TWT。

## 4. 资源与算力

- **训练集群**：4 个计算节点，每节点配备 **8 张 NVIDIA H100 GPU**（NVLink 互联）、64 核 Intel Xeon CPU、1.5 TB RAM。
- **存储**：JuiceFS 支撑的 NFS 共享，用于分布式 checkpoint 与参数同步。
- **环境集群**：独立 bare-metal Kubernetes 集群，**1024 个 CPU 核心**承载环境模拟。
- **代码规模**：约 **16 000 行 Python**，兼容 Megatron、PyTorch FSDP 等训练框架及 vLLM、SGLang 等推理框架。
- **训练时长**（隐含）：100 步文本任务、40 步多模态任务；StreamRL 在 14B 文本任务上 6 小时内未完成，TideRL 仅需其 48.9% 墙钟时间。多模态 40 步仅需 VeRL 37.8% 的墙钟时间。

## 6. 主要结论与发现

- **端到端吞吐**：在文本任务上较 VeRL 最高 **5.6×** 加速、较 AReaL **1.8×**、较 StreamRL **>7×**；在多模态任务上较 VeRL **6.02×**、较异步基线 **>1.33×**。
- **训练效率**：达到相近任务性能时文本任务训练时间下降 **51.1%**，多模态下降 **62.2%**。
- **组件贡献**：
  - CTB 把 KV cache hit rate 从 ~0.9% 提升至 >6.0%（**1.58×**），生成吞吐 **1.15×**，步时长缩短 15.6%；
  - RA²P 减少 PCIe 传输与 GPU context-switch 开销，每步训练时间最高减 **44.3%**；
  - ERS 把 RWT+TWT 最高削减 **77.6%**。
- **任务性能**：BoN 奖励与 pass rate 与 VeRL 接近（BoN 差 0.01、pass rate 差 0.5%），且优于其他异步基线。
- **Suffix decoding 失效**：在多轮异构任务上接受率仅 ~40%、平均接受长度 ~2.8 token，反而引入 4.9%–7.6% 额外开销。
- **算法有效性**：KL 惩罚天然抑制异步策略版本漂移带来的不稳定性。

---

## 7. 优点

- **统一反馈回路**：CTB → RA²P → ERS 由同一组就绪信号（RAS、TPRM）驱动，避免"独立模块各自优化"的局部最优。
- **任务级调度替代请求级调度**：语义感知优先级 + 探测式 token 预占，有效保护长上下文与活跃任务的 KV 缓存。
- **计算图重构**：把 Actor 的 loss（含 KL）推迟到 backward，与解耦 Ref 形成三阶段流水，零模型切换。
- **零开销弹性**：借力 on-policy RL 的 sync 边界天然清空 KV 缓存，避免 NCCL 组重建与 KV 物理迁移。
- **架构兼容性强**：~16 000 行 Python 模块化实现，同时支持 Megatron、FSDP、vLLM、SGLang。
- **工程细节完备**：环境侧新增 `/pause` 与 `/resume` 接口避免会话超时；Prometheus 集成用于 KV 占用、prefill/decode 延迟监控。

---

## 8. 不足与局限

- **多模态收益有限**：多模态下 Trainer 规模更大，可迁移 rank 数减少，TideRL 仅获得 33% 提升（vs. 文本 5.6×）。
- **评估任务版本锚定**：评估需固定模型版本以保证指标一致性，目前会暂时打断异步流水线；未来计划引入 Laminar 风格 relay 权重同步，但多版本 footprint 与图像轨迹共存仍待优化。
- **ERS 保守缩放**：表 2 显示 Trainer 一次只能增加一个 rank/scale-step，多模态下逐步出现"Trainer 长期瓶颈"，系统自然落入一步 off-policy。
- **Suffix decoding 兼容性差**：表 3 证实其对短接受长度、低接受率的异构多轮负载有害，目前未集成。
- **SGLang HiCache 未启用**：受主机内存限制（已被全局 trajectory buffer 与 Trainer offload 占满），放弃了另一类缓存优化。
- **环境依赖外置**：1024-core CPU 集群为高门槛假设，小规模团队难以复现；环境启动时延也是多模态吞吐受限因素之一。
- **公平性边界**：基线比例扫描的候选集固定，TideRL 起始比例也从此集合出发；若真实生产集群的初始比例显著偏离候选集，结论可能略有变化。
- **微基准规模较小**：RA²P 微基准仅用 8 个 micro-batch、4 张 H100，未覆盖更长流水线与更大 DP 组的边界情形。
