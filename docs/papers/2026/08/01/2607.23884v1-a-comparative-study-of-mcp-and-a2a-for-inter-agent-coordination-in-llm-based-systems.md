## TL;DR

这篇论文在同一软件工程任务上分别用 MCP（模型上下文协议）和 A2A（智能体对智能体协议）实现了多智能体协作系统，并从可发现性、多轮对话、异步通信、可观测性等七个维度进行了对比评估。研究发现，MCP 的实现更为轻量，适合协调需求相对简单的场景，但状态管理和任务生命周期需要在应用层手动实现；而 A2A 在协议层面提供了更丰富的有状态协调抽象，虽然使用门槛更高，却能原生支持复杂的多轮协作流程。

## 研究背景与动机

随着大语言模型能力持续增强，基于 LLM 的智能体系统正在从单智能体问答逐步演进为多智能体协作。在这类系统中，不同的智能体往往各司其职——有的负责代码生成，有的负责测试验证，有的负责需求分析——它们之间需要频繁交换信息、共享上下文、协调任务进度。这种**[[多智能体系统]]**的协调需求，与传统的分布式系统或微服务架构有着本质区别：智能体由 LLM 驱动，其输出具有不确定性，对话历史和上下文状态的管理直接影响最终效果。

然而，在实际构建这类系统时，开发者面临一个关键抉择：采用哪种协调协议来连接不同的智能体组件？业界目前存在多条技术路线，其中 MCP 和 A2A 是两个备受关注的标准。MCP 最初由 Anthropic 提出，主要目的是让 LLM 能够调用外部工具和获取上下文信息，其设计哲学强调简洁和可扩展性；A2A 则是 Google 提出的协议，旨在支持智能体之间的直接通信，特别是有状态的多轮对话和任务协作场景。两种协议的设计目标不同，适用场景也存在差异，但目前缺乏基于同一任务、同一实现深度的系统性对比研究。

这篇论文的出发点正是填补这一空白。作者团队没有停留在协议规范的文本分析层面，而是基于同一个软件工程任务，分别用 MCP 和 A2A 实现了完整的多智能体协作流程，然后从**[[协议设计]]**的角度逐项评估两种方案在真实开发场景下的表现。

## 方法

论文采用的评估方法可以概括为“需求驱动的实现对比”。作者首先从已有文献和与行业合作伙伴的讨论中提炼出多智能体协调场景的核心需求，归纳为七个评估维度：

**可发现性**关注的是智能体如何被其他组件识别和定位；**多部分消息传递**考察系统能否优雅地处理跨多条消息传输的复杂信息；**多轮对话**评估系统支持持续交互的能力；**异步通信**关注非阻塞式信息交换的便利程度；**可观测性**衡量开发者在运行时监控和调试系统的难易程度；**互操作性**评估协议与其他系统或标准集成的能力；**访问控制**则考察权限管理和安全边界的设计空间。

基于这些维度，论文选取了一个典型的软件工程任务作为测试载体——该任务需要多个 LLM 驱动的智能体相互配合，分别完成需求理解、代码实现、单元测试等子任务。选择这一场景的原因是它天然涵盖了多种协调模式：既有简单的请求-响应，也有需要维护对话上下文的复杂交互，还有跨智能体的任务委托和状态同步。

在具体实现上，研究团队为两种协议分别设计了架构方案。对于 MCP 版本，智能体通过 MCP 服务器暴露工具和资源，客户端通过协议标准化的接口调用这些工具。由于 MCP 的设计初衷是工具调用而非智能体间直接对话，研究者需要额外设计一套机制来处理会话状态和任务编排。对于 A2A 版本，智能体作为独立的任务执行者，通过 A2A 协议交换消息和任务状态，系统在协议层面直接支持任务的创建、更新、完成等生命周期事件。

## 实验与结果

论文的结果以设计观察的形式呈现，而非简单的性能指标对比。这是因为协调协议的优劣很难用单一数值衡量，更多地体现在开发体验和系统可维护性等软性维度上。

在**轻量性与实现复杂度**方面，MCP 方案展现出明显优势。由于 MCP 的协议规范相对简洁，核心实现只需关注服务器端的工具暴露和客户端的工具调用，不需要额外处理会话上下文或任务状态机。研究团队报告称，MCP 版本的代码量和配置复杂度都显著低于 A2A 版本，对于协调需求不高的场景（如简单的工具串联），MCP 能够以最小的开销完成任务。

然而，当协调需求提升到多轮对话和任务生命周期管理层面时，MCP 的局限开始显现。作者在论文中指出，MCP 本身并不提供会话状态的存储或恢复机制，智能体之间的对话历史必须由应用层负责维护。这意味着开发者在使用 MCP 构建复杂协作流程时，需要自行实现一套状态管理逻辑——包括如何持久化对话上下文、如何处理中断后的状态恢复、以及如何在不同智能体之间同步任务进展。这种“把协调问题推给应用层”的设计在短期内降低了协议复杂度，但长期来看增加了使用者的心智负担和出错可能。

A2A 则采取了不同的策略。协议原生支持**[[任务生命周期]]**的概念——每个任务都有创建、进行中、完成或失败等状态，智能体之间通过标准化的消息格式交换任务更新。这种设计使得开发者无需在应用层重新发明轮子，系统可以自动处理任务的挂起、恢复和超时等场景。与此同时，A2A 在可观测性方面也提供了更好的支持：任务状态的变化可以被日志和监控工具追踪，开发者能够清晰地看到某个任务卡在了哪个环节。

但 A2A 的代价是**[[协议设计]]**本身的复杂性显著提升。研究团队需要理解并正确实现协议规定的消息格式、状态转换和错误处理逻辑，这在原型开发阶段花费了更多时间。对于小型团队或简单场景，这种复杂性可能得不偿失。

## 讨论与可借鉴点

这篇论文最重要的贡献并非给出“MCP 更好”或“A2A 更好”的结论，而是揭示了协调协议设计中一个根本性的权衡：**把协调职责放在协议层还是应用层**。MCP 选择前者，将状态管理和任务编排交给应用层，从而保持协议的简洁和通用性；A2A 选择后者，通过丰富的协议抽象来降低应用层的实现负担，但协议的入门门槛和使用成本随之上升。

这个权衡对未来的**[[多智能体系统]]**设计和**[[协议设计]]**研究都有启发意义。对于协议制定者而言，需要在协议的通用性和场景适配性之间找到平衡——过于简单的协议会让应用层承担过多职责，过于复杂的协议又会将实现者锁死在特定的设计假设中。或许更务实的思路是设计分层的协议栈，让基础通信层保持简洁，同时在扩展层提供可选的复杂协调原语。

对于系统开发者而言，论文提醒我们在选择协调协议时不能仅看协议本身的特性，还要考虑项目的规模和团队的能力边界。原型验证阶段可以优先考虑 MCP 的轻量优势快速迭代；当系统规模扩大、需要支持更复杂的协调模式时，再考虑引入 A2A 的原生支持或自行设计应用层协调机制。

论文也坦诚地指出了研究的局限性：评估仅基于一个软件工程任务，涵盖的协调模式范围有限；结论可能不适用于其他类型的任务，如实时控制系统或大规模分布式计算；此外，研究团队对两种协议的熟悉程度可能存在差异，这也可能影响实现的公平性。这些都为后续研究留下了空间。

## 摘要
近期业界实践中，由异构的、工具与大语言模型介导的智能体组件所构成的智能体系统迅速兴起，这引发了关于智能体间协调与协议设计的现实问题。本文从多智能体系统工程视角，基于一个涉及基于大语言模型的智能体间协调场景，对模型上下文协议（Model Context Protocol, MCP）与智能体对智能体协议（Agent2Agent, A2A）进行了以实现为基础的比较。我们针对同一软件工程任务，基于从已有文献与行业合作伙伴讨论中提炼的一系列需求，包括智能体可发现性、多部分消息传递、多轮对话、异步通信、可观测性、互操作性以及访问控制，对基于 MCP 和基于 A2A 的两种多智能体实现进行了评估。结果表明，MCP 能够通过一个相对轻量、协作复杂度较低的实现模型，支持受限的基于大语言模型系统中智能体间的协调；然而，对话状态管理与任务生命周期处理等协调问题必须在应用层显式实现。相比之下，A2A 通过针对任务与生命周期管理的协议级抽象，为有状态的、多轮协调提供了更为丰富的原生支持，但其代价是实现与协调复杂度显著更高。鉴于所评估的协调模式范围有限，这些发现作为来自实证经验报告的设计观察而呈现，而非关于更广泛多智能体系统类别中协议适用性或优越性的一般性论断，旨在凸显其中的权衡取舍，以及协议抽象如何塑造当代智能体系统中协调职责的分配。

## Abstract
Recent industry practice has seen the rapid emergence of agentic systems composed of heterogeneous, tool- and LLM-mediated agent components, raising practical questions about inter-agent coordination and protocol design. This paper presents an implementation-grounded comparison of the Model Context Protocol (MCP) and the Agent2Agent (A2A) protocol, from a multi-agent systems engineering perspective, using an inter-agent coordination scenario involving LLM-based agents. We evaluate an MCP-based and an A2A-based multi-agent implementation of the same software engineering task against a set of requirements derived from prior literature and discussions with industry partners, including agent discoverability, multi-part messaging, multi-turn conversations, asynchronous communication, observability, interoperability, and access control. The results evidence that MCP can support inter-agent coordination in constrained LLM-based systems through a comparatively lightweight implementation model with lower coordination complexity, although coordination concerns such as conversational state management and task lifecycle handling must be implemented explicitly at the application layer. In contrast, A2A provides richer native support for stateful, multi-turn coordination through protocol-level abstractions for tasks and lifecycle management, but this comes with substantially greater implementation and coordination complexity. Given the narrow scope of the evaluated coordination pattern, these findings are presented as design observations from an empirical experience report rather than general claims of protocol suitability or superiority across broader classes of MAS, highlighting trade-offs and how protocol abstractions shape the distribution of coordination responsibilities in contemporary agentic systems.
