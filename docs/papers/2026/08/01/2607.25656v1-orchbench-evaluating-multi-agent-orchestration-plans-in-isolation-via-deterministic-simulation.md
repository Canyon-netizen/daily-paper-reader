## TL;DR

OrchBench 提出了一个核心问题：能否在不真正运行多[[智能体系统]]的情况下，独立评估"如何分配任务、如何在智能体间传递信息"这一编排决策的质量？答案是肯定的——它用[[有向无环图]]编码任务依赖关系，通过确定性模拟器在隔离环境中评测编排计划的质量、时延与 token 成本。实验证明，模拟评分与 Claude Code 真实执行的皮尔逊相关系数高达 $r=0.816$，而开销仅为真实执行的 1.3% tokens 和 10.3% 时间。更重要的是，这套框架揭示了一个反直觉的结论：保留关键信息比单纯增加智能体数量更重要，且并行化收益会随协调失败的累积而递减。

## 研究背景与动机

多智能体系统近年来在复杂任务处理上展现出强大的能力，一个典型的工作流可能包含数十个相互依赖的子任务，需要多个智能体协同完成。在这种架构下，"编排"——即如何将子任务分配给不同智能体、如何控制它们之间的信息传递——直接影响最终结果的质量、执行速度和资源消耗。然而，如何科学地评估一个编排计划的好坏，长期以来缺乏统一的方法论。

现有评估通常采用端到端执行的方式：将编排计划交给真实的多智能体系统运行，观察最终输出质量。这种做法存在一个根本性缺陷——它将编排计划的优劣与智能体的能力、工具的可靠性、环境的噪声等因素混为一谈。想象一个场景：编排计划本身设计得很糟糕，但由于每个智能体都足够强大，最终结果依然可接受；反过来，一个精妙的编排计划可能因为某个智能体的偶发故障而崩溃。在端到端评估中，这两类问题完全无法区分。更棘手的是，随着工作流规模扩大，真实执行所需的 token 消耗和时间成本急剧膨胀，使得在同一批任务上系统性地横向比较多个编排方案变得代价高昂。

这一困境催生了一个关键问题：能否构建一个独立的评估基准，在不实际调用工作智能体的前提下，单独度量编排决策本身的质量？这需要解决三个子问题：第一，如何用统一的数学语言描述任务结构与编排决策；第二，如何在隔离环境中模拟编排计划的执行结果；第三，如何保证模拟结果与真实执行的一致性。OrchBench 正是针对这三个问题给出的系统性回答。

## 方法

OrchBench 的设计围绕一个核心洞察：编排计划本质上是一个关于"谁来做什么、何时做、如何交换信息"的决策，而任务的结构——哪些子任务依赖于哪些前置结果——可以用[[有向无环图]]（DAG）精确表达。这个洞察使得在隔离环境中模拟编排成为可能。

整个流程分为三个阶段。首先是 DAG 构造阶段。OrchBench 从真实任务池（涵盖金融分析、数据科学问答、SQL 生成等场景）出发，通过迭代 refinement 循环逐步生成 DAG。每轮迭代中，生成器根据种子任务创建候选 DAG，结构判官验证其深度、扇出、依赖密度等属性是否符合目标规格，语义判官确保子任务之间的依赖关系在逻辑上成立。这个过程持续进行，直到生成的 DAG 同时满足指定的子任务数量 $n$ 和自然并行度指标 $\frac{k_{99}(G)}{n}$。这里的 $k_{99}(G)$ 是一个精心设计的概念：它表示使得完工时间达到关键路径长度 99% 以内所需的最小智能体数量，$k_{99}/n$ 越大说明该任务越容易被并行化。

第二阶段是编排规划。给定 DAG、每个智能体的上下文限制 $L$ 以及智能体预算 $A_{\max}$，被评估的规划器需要输出一份 JSON 格式的 workflow script。这份脚本声明智能体池的配置（总数不超过 $A_{\max}$）、每个子任务的分配规则（支持轮询、依赖分组、负载均衡等策略）、以及跨智能体的信息传递规则。值得注意的是，跨 agent 依赖必须显式声明，缺失的传递会被记录为"missing transfer"并受到质量惩罚——这个设计直接度量了规划器对依赖关系的把握程度。

第三阶段是确定性模拟。模拟器按照拓扑顺序处理每个子任务，分六个步骤进行。首先检查所有父任务是否已完成；其次根据依赖关系和智能体的当前状态计算启动时间；第三步获取执行上下文，同 agent 的父结果直接复用，跨 agent 的结果按声明的压缩比 $e$ 复制——如果未声明，则记为 missing transfer，父任务的贡献质量按因子 $\lambda$ 折损；第四步处理上下文管理，当累计 token 超过 $L$ 时执行压缩，压缩后的 token 数和保留质量分别由公式决定；第五步模拟子任务执行，质量由父任务质量的几何平均与压缩指数共同决定；最后更新智能体时钟和本地内存。

模拟器返回三个核心指标：最终质量 $Q$（终任务质量的宏平均）、时间效率 $E_{\text{time}} = \min(1, C/M)$（关键路径长度与实际完工时间的比值）、以及 token 效率 $E_{\text{token}} = \min(1, T_{\text{single}}/T)$（单智能体 baseline 与实际 token 消耗的比值）。最终综合分数取三者均值。

## 实验与结果

OrchBench 的实验设计围绕一个核心验证目标展开：模拟评分能否可靠预测真实执行的表现？研究团队构建了包含 240 个 DAG 的基准测试，覆盖从 10 到 1000 个子任务的多种规模，并与 Claude Code、SWE-mini、OpenHands、Crush 四套真实框架进行对齐实验。

保真度验证是首要任务。结果显示，OrchBench 产生的模拟评分与 Claude Code 真实执行的质量分数达到 Pearson 相关系数 $r=0.816$、Spearman 秩相关系数 $\rho=0.771$。更严格的 leave-one-model-out 实验（即每次去掉一个模型后重新计算相关性）全部保持正相关，表明这一相关性不是由某个特定模型驱动的。值得注意的是，当排除 GLM-5.1 后，相关系数跃升至 $r=0.949$——这暗示该模型在编排规划上存在某种系统性的"作弊"策略，使得模拟器无法准确捕获其在真实环境中的表现。

效率提升同样显著。在 WideSearch 任务上，真实执行需要消耗 17.35M tokens 并耗时 56.13 分钟，而 OrchBench 仅需 44.61K tokens 和 0.51 分钟，分别节省了 389 倍和 110 倍。在 MultiAgentBench 上，节省比例分别为 74 倍和 9.7 倍。综合来看，OrchBench 只需 1.3% 的 tokens 和 10.3% 的时间即可获得与真实执行高度相关的结果。

实验还揭示了两个重要的洞察。第一个关乎智能体数量与信息保留的关系：当 DAG 规模达到 100 个子任务时，智能体数量与最终质量的相关性骤降至 $-0.021$——几乎无关。相比之下，跨 agent 传递覆盖率（即是否正确声明了所有必要的依赖信息）与质量的相关性持续保持在 $0.614$ 到 $0.952$ 的高水平。这一发现有力地证明了"保留关键信息"比"增加智能体数量"对编排质量的影响更为深远。第二个洞察涉及并行化收益的衰减：随着 missing transfer 的累积（即规划器遗漏了更多依赖关系），原本通过并行化应该获得的时间收益被逐渐蚕食，当协调失败率达到一定程度后，增加并行度反而可能带来负面影响。

## 讨论与可借鉴点

OrchBench 最直接的价值在于为多[[智能体系统]]研究提供了一个高效、可控的实验平台。传统评估方式需要在真实环境中反复运行工作流，成本高昂且难以定位问题根源；OrchBench 通过将编排决策从执行细节中解耦，使得研究者能够以极低的代价系统性地探索编排策略的空间。这一点对于工程实践同样有意义——在部署到生产环境之前，可以用 OrchBench 快速筛选候选编排方案，估计任务难度，甚至指导 workflow 的迭代优化。

然而，这项工作也存在一些局限性需要正视。首先，模拟器对规划器的能力做了若干简化假设——例如假设每个子任务的执行时间是固定预算、假设压缩对质量的影响可以用指数模型近似——这些假设在真实场景中未必成立。其次，模拟器无法捕获真实执行中的非确定性因素，如工具调用的随机失败、API 的响应波动等，这些因素在实际系统中往往不可忽视。第三，虽然模拟评分与真实质量高度相关，但对于 token 消耗和执行时间的预测精度较低（分别为 $-0.607$ 和 $-0.264$），这意味着如果应用场景对资源成本敏感，仍需结合真实执行数据进行校准。

从更宏观的视角看，OrchBench 提出的问题框架——如何独立评估复杂系统中某个组件的决策质量——具有超越多智能体领域的普遍意义。任何涉及多层抽象、组件协作的系统，其整体性能都可以分解为"架构设计"和"执行质量"两个维度，而两者的分离评估正是系统化优化的前提。未来的工作可以在这个方向上进一步探索，例如将类似的思想推广到 agent 记忆管理、工具选择等更细粒度的决策问题，或者构建更大规模、更多样化的 DAG 库以提升基准测试的覆盖度。

## 摘要
复杂任务通常可以分解为可并行但相互依赖的子任务，这使得编排对多智能体系统（MAS）的性能至关重要。现有评估通常依赖端到端执行，这种方式将编排计划的质量与智能体能力、工具可靠性以及环境噪声混为一谈。此外，随着工作流规模的扩大，实际执行所需的时间和令牌成本迅速增长，使系统性评估变得代价高昂。我们提出了 OrchBench，这是一个基于模拟的基准测试，用于在隔离环境下评估多智能体编排计划。OrchBench 从真实任务出发，构建表示任务依赖关系的有向无环图（DAG），并控制其规模与并行度。给定一个 DAG、每个智能体的上下文限制以及智能体预算，被评估的规划器将子任务分配给各智能体，并指定跨智能体的信息传输及其保留比率。一个确定性模拟器在不调用工作智能体的情况下评估所生成的计划，并返回关于结果质量、完工时间与令牌成本的可解释度量。OrchBench 所产生的模拟分数与 Claude Code 执行所获得的质量分数具有强相关性，皮尔逊相关系数达到 r=0.816，同时仅需 1.3% 的令牌和 10.3% 的挂钟时间。在不同的规划器与工作流规模下，我们发现保留任务关键信息比单纯增加智能体数量更为重要，并且随着协调失败的累积，并行化所带来的收益逐渐减小。上述结果确立了 OrchBench 作为一种高效且可解释的基准测试，可用于比较和诊断多智能体编排计划。

## Abstract
Complex tasks often decompose into parallelizable yet interdependent subtasks, making orchestration critical to the performance of multi-agent systems (MAS). Existing evaluations typically rely on end-to-end execution, which conflates orchestration-plan quality with worker capabilities, tool reliability, and environmental noise. Moreover, the time and token costs of real execution grow rapidly with workflow scale, making systematic evaluation expensive. We present OrchBench, a simulation-based benchmark for evaluating multi-agent orchestration plans in isolation. Starting from real-world tasks, OrchBench constructs directed acyclic graphs (DAGs) that encode task dependencies, with controlled sizes and degrees of parallelism. Given a DAG, a per-agent context limit, and an agent budget, the evaluated planner assigns subtasks to agents and specifies cross-agent information transfers and their retention ratios. A deterministic simulator evaluates the resulting plan without invoking worker agents and returns interpretable measures of result quality, makespan, and token cost. The simulated scores produced by OrchBench correlate strongly with quality scores from Claude Code executions, achieving a Pearson correlation of \(r=0.816\), while requiring only \(1.3\%\) of the tokens and \(10.3\%\) of the wall-clock time. Across diverse planners and workflow scales, we find that preserving task-critical information is more important than simply increasing the number of agents, and the benefits of parallelism diminish as coordination failures accumulate. These results establish OrchBench as an efficient and interpretable benchmark for comparing and diagnosing multi-agent orchestration plans.

## 2. 方法论

### 2.1 整体三阶段流程

1. **DAG 构造**：把真实世界种子任务转成带依赖的 DAG。
2. **编排规划**：给定 DAG、上下文限制 $L$、agent 预算 $A_{\max}$，由待评估规划器 $F_\theta$ 输出 JSON 格式的 `workflow_script`。
3. **确定性模拟**：解释器展开脚本得到具体计划 $\pi=(\alpha, R)$，由模拟器在不调用任何 LLM worker 的前提下评估计划并产出可解释分数。

### 2.2 问题形式化

- 任务实例为 DAG $G=(V,E)$，节点 $v$ 表子任务，边 $(u,v)$ 表依赖。
- 每个子任务带输入/执行/输出 token 预算 $(x_v^{\text{in}}, x_v^{\text{exec}}, x_v^{\text{out}})$、时间预算 $\tau_v$、压缩敏感性 $c_v\in\{\text{robust},\text{balanced},\text{fragile}\}$。
- 计划 $\pi=(\alpha,R)$：
  - 分配函数 $\alpha: V \rightarrow \{1,\dots,A_{\max}\}$；
  - 跨 agent 传递比率 $R(u,v)=e\in(0,1]$；
  - 同 agent 子任务复用为 100% 本地重用；缺失的跨 agent 传递记为 **missing transfer**；多余的传递记为非法。
- 模拟器返回最终质量 $Q$、完工时间 $M$、总 token 成本 $T$。

### 2.3 自然并行度指标

$$\frac{k_{99}(G)}{n},\quad k_{99}(G)=\min\{k: \text{ms}_k(G)\le C(G)+0.01(W(G)-C(G))\}$$

其中 $W(G)$ 为所有子任务串行总时间，$C(G)$ 为关键路径长度，$\text{ms}_k(G)$ 为 $k$ 个 worker 下的 makespan。$k_{99}/n$ 越大表示该 DAG 自然并行度越高。

### 2.4 DAG 构造（迭代 refinement loop）

- 从问题池 $D$（Finance Agent、DS-1000、Qasper、BIRD-SQL）抽样种子；
- 经 **种子筛选器** → **生成器** → **结构判官 + 语义判官** 反复修订，直至子任务数 $n$ 与并行度桶 $k_{99}/n$ 同时达标；
- 输出问题包 $P=(G,L)$。

### 2.5 编排规划脚本

- `agent_pools`：命名池，总规模 $\le A_{\max}$；
- `rules`：按 stage/stages/regex/task_ids 匹配任务，分配策略支持 `round_robin / dependency_grouping / load_balance / single`；
- `default`：未匹配任务的兜底规则；
- `transfer_rules`：声明跨 agent 依赖及压缩比 $e$；
- 关键约束：**跨 agent 依赖必须显式声明**，否则被记录为缺失并被质量惩罚。

### 2.6 确定性模拟器（Algorithm 1）

模拟器按**拓扑顺序**处理每个子任务 $v$，依次执行六个阶段：

1. **依赖解析**：所有父任务必须完成。
2. **Agent 调度**：启动时间为

$$s_v = \max\left(c_a,\; \max_{u\in \text{Parents}(v)} f_u\right) \tag{1}$$

3. **上下文获取**：
   - 同 agent 父结果直接重用；
   - 跨 agent 且 $R$ 已声明时按压缩比 $e$ 复制并计入通信 token 与保留质量；
   - 跨 agent 但**未声明**时记 missing transfer，父贡献质量乘以 $\lambda$（默认 0.5）。
4. **上下文管理**：超过 $L$ 时反复压缩，压缩后 token 与质量分别为

$$n'_v=\lceil e\, n_v\rceil,\quad q'_v=\max(q_{\min},\, q_v\, e^{s_v}) \tag{2}$$

5. **子任务执行**：质量由父质量的几何平均与压缩指数共同决定，

$$q_v = \text{clip}_{[q_{\min},1]}\!\left(\bar{q}^{\,e^{s_v}}\right) \tag{3}$$

6. **状态更新**：完成时间为 $f_v = s_v + \tau_v + \Delta_v^{\text{post}}$，更新 agent 时钟与本地内存，释放无用父包。

压缩类对应指数 $\gamma\in\{0.35,0.85,1.25\}$，最小保留率 $\in\{0.08,0.22,0.55\}$；不同压缩类保留不同的时间/token 开销。

### 2.7 评分指标

- **质量** $Q = \frac{1}{|T|}\sum_{w\in T} q_w$（终任务宏平均）；
- **时间效率** $E_{\text{time}} = \min\!\left(1,\; C/M\right)$；
- **Token 效率** $E_{\text{token}} = \min\!\left(1,\; T_{\text{single}}/T\right)$；
- **总分**：

$$\text{Score} = \frac{Q + E_{\text{time}} + E_{\text{token}}}{3} \tag{7}$$

## 6. 主要结论与发现

- **保真度**：OrchBench 与 Claude Code 真实执行在 final score 上达到 **Pearson $r=0.816$**、**Spearman $\rho=0.771$**，leave-one-model-out 全部为正相关，去掉 GLM-5.1 后 $r$ 提升至 0.949；
- **效率**：仅需 1.3% tokens、10.3% 墙钟时间；WideSearch 上节省 389×/110×，MultiAgentBench 上节省 74×/9.7×；
- **跨框架稳健**：与 Claude Code、SWE-mini、OpenHands、Crush 四套框架的 OrchBench 模拟相关均为正；
- **保留信息比增 agent 更重要**：100 任务时 agent 数与质量的相关性降至 $-0.021$，而**传递覆盖率**与质量相关性持续为 $0.614$–$0.952$；
- **规模越大协调越脆弱**：$n=500\to1000$ 时，Claude 覆盖率从 0.981 跌至 0.441（缺传 872），DeepSeek 跌至 0.398（缺传 907），而 Gemini 仍保持完整覆盖；
- **并行收益递减**：$A_{\max}$ 从 16 增至 64 时 agent 数翻倍但分数几乎不变；
- **多 agent 何时真正有用**：在 $L=16$k 时多 agent 带来 +0.302 质量提升；$L=128$k 时仅 +0.007，且 82% 的模型-问题对中多 agent 质量反而更低——**当工作状态能装进单个上下文窗口时，多 agent 反而成为纯协调开销**；
- **诊断能力**：模拟器可直接识别 missing transfer 等协调失败；模拟引导的 refinement 在真实执行中将平均分从 3.754 提升至 4.150；
- **预算受限下的样本选择**：按模型分歧度选 5 个任务即可达到 Spearman 0.754、配对准确率 0.800，远超随机选样。

## 7. 优点

- **问题重新定义清晰**：将"编排质量"从端到端评估中拆出，单独形式化为基准问题；
- **DAG 构造方法学扎实**：含 seed judge、结构 judge、语义 judge 与迭代 refinement，且提供 6 维验证；
- **模拟器忠实度高**：六阶段生命周期（依赖解析→调度→上下文获取→上下文管理→执行→状态更新）映射真实框架行为，确定性带来可重复性；
- **机制设计有针对性**：显式建模跨 agent 传递、缺失传递惩罚 $\lambda$、压缩敏感度（robust/balanced/fragile）与最小保留率，使强/弱规划者差异不被饱和（消融实验验证）；
- **可解释诊断**：直接暴露 missing transfer、压缩次数、覆盖率等可归因信号；
- **实证价值高**：覆盖 9 个主流 LLM、4 种真实框架、5 个规模区间，含极限尺度 $n=1000$；
- **直接可工程化**：模拟引导的 refinement 在真实系统中验证有效，模型预筛选/任务难度估计展示实用落地路径。

---

## 8. 不足与局限

- **不评估真实 worker 与工具**：刻意剥离 worker 推理与工具可靠性，故无法反映真实端到端表现；
- **时间/token 与真实相关性弱**：因框架相关，OrchBench 不能可靠预测实际墙钟与 token；
- **真实工具失败、长尾异常、限流等待未建模**：虽保留元数据用于可选争用研究，但默认关闭；
- **未覆盖动态重编排**：任务依赖 $G$ 被固定为输入，不考察运行时重排、agent 失败恢复等场景；
- **规划输出受限于 JSON 脚本范式**：要求模型输出结构化 workflow_script，部分模型需要 repair 调用，能力较弱的模型可能直接得零分；
- **评分对极端情况敏感**：如 $\lambda=1$ 时质量差几乎消失，机制贡献需小心调参；
- **模型多样性受限于可用 API**：GLM-5.1 与 Gemini 在不同规模下系统性占优，可能受 prompt 与脚本格式偏好的影响；
- **单一主调用策略**：每对模型-问题只生成 1 次主规划 + 1 次 repair，未做多次随机种子估计方差；
- **应用层面尚未涵盖**：实时 agent 框架中的隐私、合规、人机协作等约束被忽略；
- **DAG 失败率约 34.3%**：大尺度 DAG 易出现冗余/重复子任务，DAG 质量仍依赖生成器-judge 协作效果。
