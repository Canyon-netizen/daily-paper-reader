## TL;DR

这篇论文以同一软件工程任务为载体，实现并对比了 MCP 与 A2A 两种智能体间协调协议。研究发现，MCP 实现轻量（1255 行代码）、协调复杂度低，但多轮对话等能力需要开发者在应用层手动构建；A2A 则在协议层内置了任务生命周期管理和状态化协调支持，代价是实现代码量增加约 51%，协调阶段从 2 步升至 6 步。该工作以实证经验报告的形式揭示了协调职责如何在协议层与应用层之间分配，而非给出协议优劣的绝对判断。

## 研究背景与动机

过去几年间，由大语言模型驱动、通过工具与外部世界交互的智能体系统迅速崛起。无论是代码生成、数据分析还是自动化工作流，越来越多的系统开始由多个分工明确的智能体组件构成——这催生了一个根本性的工程问题：这些智能体之间应该如何通信与协调？

从学术脉络看，经典多智能体系统研究早已积累了丰富理论，强调智能体的自主性、反应性、社会交互能力。但在当代 LLM 系统中，"智能体"的概念已发生漂移：它更常被理解为 LLM 驱动的、能执行多步骤任务的组件，而非传统意义上具有强自主意识的社会实体。这种语境切换带来了新的实践困惑——当系统需要多个 LLM 智能体协同完成复杂任务时，现有的协议与框架是否足够好用？

业界目前主流的两套方案走向了不同方向。**MCP**（Model Context Protocol）最初由 Anthropic 提出，旨在解决 LLM 与外部工具、数据源的连接问题——它定义了标准化的接口，让模型可以调用各类资源和服务。**A2A**（Agent-to-Agent Protocol）则由 Google 等厂商倡导，专为异构智能体之间的通信与协作设计，支持任务委派、状态追踪和多轮对话。

一个自然的疑问随之浮现：既然许多系统已经基于 MCP 实现了丰富的工具生态，是否可以复用这套协议来处理智能体之间的协调？还是说必须引入专门的 A2A 协议？这个问题在业界存在广泛争议，但缺乏来自真实实现的实证证据。论文的切入点正在于此——不是从规范文档出发做理论推演，而是把两种协议都跑起来，用同一个任务、同样的协作结构来比较它们在工程实践中的真实表现。

## 方法

作者采用了一种实现驱动的实证方法，核心思路是控制变量：固定协作结构和任务定义，只替换底层协议，从而隔离协议抽象本身带来的影响。

任务设定具有代表性——让智能体将自然语言描述转换为 **Emfatic** 语言（一种用于 Eclipse 建模框架的文本表示），最终产出面向对象的领域模型。这个过程天然需要多轮迭代：生成初始模型后，需要经过语法检查和语义验证，必要时根据反馈重新生成。整个工作流对应了现代智能体系统中常见的"规划—执行—验证"循环模式。

协作架构由四类角色组成。**协调智能体**负责编排整个工作流程，但它本身不使用 LLM，仅做流程控制。**方案智能体**基于 `qwen2.5-coder:32b` 开源模型生成 Emfatic 模型，可以采用 ReAct 模式调用内部工具。**语法监督智能体**用 Java 实现的 Emfatic 解析器进行形式化验证。**语义监督智能体**则通过 few-shot prompt 的方式，基于 LLM 判断模型是否符合用户的原始需求描述。

两种协议实现共享完全相同的协作逻辑，但协议层的抽象方式截然不同。在 MCP 版本中，每个智能体被封装为一个 MCP server，server 中定义一个工具，操作智能体实际上就是调用工具。协作通过客户端-服务器模式展开，消息传递被包裹在工具调用的请求-响应结构中。

A2A 版本则充分利用协议提供的原生能力。任务通过 task ID 持久标识，上下文通过 context ID 追踪。协议定义了 `TaskStatusUpdateEvent` 用于生命周期状态推送，`TaskArtifactUpdateEvent` 用于传递生成的产物，多部分消息和流式传输也被纳入规范。这种设计天然支持长时间运行的多轮任务：委派方可以发起任务后等待反馈，被委托方可以返回"需要输入"状态让对方补充信息。

为了评估的全面性，作者从文献调研和业界合作伙伴（包括银行、航空航天、物联网等行业的实际用例）中提炼出七项工程需求，涵盖智能体可发现性、多部分消息传递、多轮对话、异步通信、可观测性、互操作性以及访问控制。这些需求构成了后续评估的维度。

## 实验与结果

实验的核心是对比表直观呈现了两种协议的工程代价差异。MCP 实现仅需 1255 行代码，而 A2A 实现达到 1898 行，增幅约 51%。更显著的差异在于协调复杂度：MCP 方案仅需 4 个协调原语、2 个协调阶段即可完成一次交互；A2A 方案则需要 10 个协调原语和 6 个协调阶段。这是因为 A2A 的每个操作都需要显式处理任务状态转换、事件订阅、产物注册等多个协议规定的步骤。

在需求满足度的定性评估中，两种协议呈现出有趣的分歧。MCP 能够满足可发现性、多部分消息、异步通信、互操作性和访问控制这几项需求，但**无法原生支持多轮对话**——当协作需要在多个步骤之间传递上下文时，MCP 缺乏会话状态的协议级抽象，开发者必须在应用层自行实现状态管理逻辑。相比之下，A2A 完整支持所有七项需求，其协议规范中明确包含了多轮对话所需的 task lifecycle 和状态机机制。

两种实现都集成了 Langfuse 进行可观测性追踪，通过 OpenTelemetry traces 记录智能体行为，便于调试和问题诊断。

值得注意的是，作者多次强调这些发现属于"设计观察"而非普适结论。实验仅使用 30 条 prompt 进行功能验证，未构成统计意义上的 benchmark，也未进行性能基准测试（如时延、吞吐量、token 消耗的量化对比）。评估方式以定性需求满足度判定为主，带有一定主观性，但评估维度本身来自真实的业界需求提炼。

## 讨论与可借鉴点

论文最重要的启示在于揭示了**协调职责的分配问题**。MCP 和 A2A 的本质差异不是谁"更好"，而是协调能力在协议层还是应用层实现的选择。MCP 把协议设计得简洁，代价是把复杂性推给了开发者；A2A 把协议设计得完备，代价是开发者在使用每个功能时都要遵循更繁琐的交互模式。

这种权衡具有实际指导意义。对于轻量级场景——比如一次性的请求、明确的输入输出、不需要跨多次调用维护状态——MCP 的简单模型足以胜任，引入 A2A 的复杂度反而是过度工程。反过来，如果系统需要处理长时间运行的任务、在多个步骤之间维护上下文、或者让智能体之间进行真正的对话式协商，A2A 提供的协议级抽象能显著降低应用层代码的维护负担。

论文也坦诚地指出了局限性。评估仅限于一种固定协作模式——任务委派加上基于反馈的迭代细化——并未涉及动态协商、竞争拍卖、层级控制等更复杂的多智能体交互形态。此外，实验未与其他协议（如传统多智能体系统中的 KQML、FIPA-ACL，或新兴的 ACP、ANP）进行对比，也未探索两种协议混合使用的可能性。

一个值得关注的探索方向是论文末尾提到的可能性：利用 MCP 的资源/工具机制暴露共享通信构件（如 mailbox、task queue），在不引入新协议的前提下为 MCP 添加有状态协调能力。这种"协议内复用"思路若能成功，将为已有 MCP 基础设施的团队提供一条渐进式演进路径。

总体而言，这项工作为正在设计多智能体系统的工程师提供了一份实用的参考框架——不是告诉你该选哪个协议，而是让你理解选择背后的工程代价，从而根据具体场景做出更明智的决策。

## 摘要
近期业界实践中，基于异构的、由工具和大语言模型介导的智能体组件所构成的智能体系统迅速涌现，由此引发了关于智能体间协调与协议设计的实践性问题。本文从多智能体系统工程视角出发，以涉及基于大语言模型的智能体的智能体间协调场景为案例，对模型上下文协议（MCP）与智能体对智能体（A2A）协议进行了基于实现的对比研究。我们依据既有文献与业界合作伙伴讨论所提炼出的一系列需求，对同一软件工程任务的两种多智能体实现——一种基于 MCP、一种基于 A2A——进行评估，这些需求涵盖智能体可发现性、多部分消息传递、多轮对话、异步通信、可观测性、互操作性以及访问控制。结果表明，MCP 能够通过一种相对轻量、具备较低协调复杂度的实现模型，在受限的基于大语言模型的系统中支持智能体间的协调，但诸如对话状态管理与任务生命周期处理之类的协调问题必须在应用层显式实现。相比之下，A2A 通过面向任务与生命周期管理的协议级抽象，为有状态的、多轮协调提供了更丰富的原生支持，但这也带来了显著更高的实现与协调复杂性。鉴于所评估的协调模式范围有限，这些发现作为来自实证经验报告的设计观察加以呈现，而非对协议在更广泛多智能体系统类别中的适用性或优越性所作的普适性论断，旨在凸显其中的权衡取舍，以及协议抽象如何塑造当代智能体系统中协调职责的分配。

## Abstract
Recent industry practice has seen the rapid emergence of agentic systems composed of heterogeneous, tool- and LLM-mediated agent components, raising practical questions about inter-agent coordination and protocol design. This paper presents an implementation-grounded comparison of the Model Context Protocol (MCP) and the Agent2Agent (A2A) protocol, from a multi-agent systems engineering perspective, using an inter-agent coordination scenario involving LLM-based agents. We evaluate an MCP-based and an A2A-based multi-agent implementation of the same software engineering task against a set of requirements derived from prior literature and discussions with industry partners, including agent discoverability, multi-part messaging, multi-turn conversations, asynchronous communication, observability, interoperability, and access control. The results evidence that MCP can support inter-agent coordination in constrained LLM-based systems through a comparatively lightweight implementation model with lower coordination complexity, although coordination concerns such as conversational state management and task lifecycle handling must be implemented explicitly at the application layer. In contrast, A2A provides richer native support for stateful, multi-turn coordination through protocol-level abstractions for tasks and lifecycle management, but this comes with substantially greater implementation and coordination complexity. Given the narrow scope of the evaluated coordination pattern, these findings are presented as design observations from an empirical experience report rather than general claims of protocol suitability or superiority across broader classes of MAS, highlighting trade-offs and how protocol abstractions shape the distribution of coordination responsibilities in contemporary agentic systems.

## 1. 核心问题与研究背景

随着大语言模型（LLM）驱动的智能体系统迅速兴起，业界出现了大量由异构、工具中介、LLM 介导的智能体组件构成的"智能体系统"（agentic systems），使得**智能体间的协调（inter-agent coordination）** 成为突出的工程实践问题。

- 在经典多智能体系统（MAS）文献中，Wooldridge 提出的"弱主体性"概念强调自主性、反应性、主动性以及通过显式通信机制与其他智能体交互。在当代 LLM 系统中，"智能体"更常被定义为 LLM 驱动的、能在软件系统中执行多步骤任务的组件（类似 LangChain 的定义）。
- 两大主流协议被广泛使用：**模型上下文协议（MCP）**（主要用于 LLM 与工具/数据源的接入）与 **智能体对智能体协议（A2A）**（专为异构智能体间通信与协作设计）。
- 学界与业界通常将二者视为"互补"而非"竞争"关系（MCP 用于 agent-to-tool，A2A 用于 agent-to-agent），但在 LLM 系统中（已有 MCP 工具集成基础时）究竟应否复用 MCP 支持智能体间协调、还是必须引入 A2A，业界存在争议。
- 本研究的目标是：从 MAS 工程视角，对 MCP 与 A2A 在同一智能体间协调场景下的实现进行**基于实现的实证比较**，揭示协议抽象如何影响协调职责在协议层与应用层之间的分配。

## 2. 方法论

### 2.1 核心思想

- 采用**实现驱动（implementation-grounded）的实证经验报告**形式，固定协作结构、控制变量，重点比较协议抽象对协调复杂度的影响。
- 采用一种**窄但具代表性**的协调模式：任务委派 → 迭代细化（基于反馈） → 验证，对应于当代智能体系统中常见的"规划—执行—验证"循环。

### 2.2 关键技术细节

- **任务定义**：给定自然语言 prompt，生成 **Emfatic**（Eclipse Modeling Framework 的文本语言）表示的面向对象领域模型，便于自动生成 Java 代码与文档。
- **协作结构（固定协作算法）**：

$$
\begin{array}{l}
\textbf{Algorithm 1: Collaboration Agent Workflow for Model Generation} \\
\textbf{Input: } \text{User prompt } P,\ \text{maximum retries } N \\
\textbf{Output: } \text{Validated artifact } M \text{ or failure} \\
\hline
attempts \leftarrow 0,\ validated \leftarrow \text{false} \\
\textbf{while } attempts < N \ \textbf{and not } validated: \\
\quad attempts \leftarrow attempts + 1 \\
\quad M \leftarrow \text{SolutionAgent.Generate}(P) \\
\quad syntaxFeedback \leftarrow \text{SyntacticSupervisorAgent.Validate}(M) \\
\quad \textbf{if } \text{syntaxFeedback.status} = \text{invalid}: \\
\qquad P \leftarrow \text{RefinePrompt}(P,\ \text{syntaxFeedback});\ \textbf{continue} \\
\quad semanticFeedback \leftarrow \text{SemanticSupervisorAgent.Validate}(P,\ M) \\
\quad \textbf{if } \text{semanticFeedback.status} = \text{invalid}: \\
\qquad P \leftarrow \text{RefinePrompt}(P,\ \text{semanticFeedback});\ \textbf{continue} \\
\quad validated \leftarrow \text{true} \\
\textbf{return } M \text{ if } validated \text{ else } failure
\end{array}
$$

- **角色构成**：
  - **Collaboration Agent（协调智能体）**：编排整个工作流，不使用 LLM；
  - **Solution Agent（方案智能体）**：基于 `qwen2.5-coder:32b` LLM 生成 Emfatic 模型，可采用 ReAct 架构调用内部工具；
  - **Syntactic Supervisor Agent（语法监督智能体）**：用 Java 实现的 Emfatic 解析器检查语法；
  - **Semantic Supervisor Agent（语义监督智能体）**：基于 LLM（few-shot prompt）评估模型是否符合 prompt 描述。
- **两种协议实现**：
  - **MCP 实现**：每个智能体暴露为 MCP server（每个 server 含一个工具），通过 MCP client 调用工具；智能体行为被工具封装（root-level tool ≈ agent）。
  - **A2A 实现**：利用 task ID、context ID 持久标识；通过 `TaskStatusUpdateEvent`、`TaskArtifactUpdateEvent`、`Message`、Part 类型实现任务生命周期、产物管理与流式通信；显式支持 `input-required`、`auth-required`、`completed`、`cancelled`、`failed`、`rejected` 等状态。
- **可观测性**：两种实现均集成 Langfuse，发送 OpenTelemetry traces。

### 2.3 评估需求维度（R1–R7）

| 需求 | 描述 |
|---|---|
| $R_1$ | 智能体可发现性（discoverability） |
| $R_2$ | 多部分消息（multi-part messaging） |
| $R_3$ | 多轮对话（multi-turn conversations） |
| $R_4$ | 异步与流式通信（asynchronous / streaming） |
| $R_5$ | 智能体可观测性（observability，含 super-task ID） |
| $R_6$ | 互操作性（interoperability，多语言、跨框架） |
| $R_7$ | 访问控制（access control） |

需求源自既有协议调研文献与 MOSAICO 项目中银行、航空航天、沉浸式技术、IoT 等行业合作伙伴的实际用例。

## 3. 实验设计

- **场景/任务**：以"自然语言 → Emfatic 面向对象领域模型"为软件工程任务；通过协作算法实现"生成—语法验证—语义验证—迭代细化"的闭环。
- **数据集/基准**：使用 **30 条验证 prompt**，其中 10 条简单、20 条复杂度较高（具体 prompt 见 [9]）。文章同时给出了一个示例 prompt（图书馆领域模型，含 Library / Book / Author 三概念）与对应的有效 Emfatic 输出。
- **对比方法**：
  - **MCP-based 多智能体实现**（Java + Python，基于 MCP SDK）；
  - **A2A-based 多智能体实现**（Java + Python，基于 A2A SDK）；
  - 两个实现**共享相同的协作结构**，仅协议层不同，以便隔离协议抽象的影响。
- **未做**：与传统 MAS 协议（如 KQML、FIPA-ACL）的对比、与其他新兴协议（ACP、ANP）的对比。

- **实验规模**：
  - 仅 30 条 prompt 用于功能性验证；

## 6. 主要结论与发现

1. **MCP 支持受限场景下的智能体间协调**，实现轻量、协调复杂度低；但会话状态管理与任务生命周期需在**应用层显式实现**。
2. **A2A 提供更丰富的协议级抽象**（task、lifecycle、状态机、多部分消息），天然支持有状态、多轮协调；代价是**实现与协调复杂度显著更高**（LOC 增加约 51%，协调原语和阶段更多）。
3. **量化对比结果**（表 1）：

$$
\begin{array}{l|ccc}
\text{Metric} & \text{MCP} & \text{A2A} \\
\hline
\text{Lines of code} & 1255 & 1898 \\
\text{Coordination primitives} & 4 & 10 \\
\text{Coordination stages per interaction} & 2 & 6 \\
\end{array}
$$

4. **需求满足度对比**（表 2）：MCP 满足 $R_1, R_2, R_4, R_6, R_7$；部分满足 $R_5$；**不满足** $R_3$（多轮对话）。A2A 满足 $R_1, R_2, R_3, R_4, R_6, R_7$；部分满足 $R_5$。**关键差异**：多轮、有状态任务处理——A2A 提供协议级支持，MCP 需应用层自行实现。
5. 协议抽象的**设计权衡**：MCP 适合轻量、一次性、请求—响应式的协调；A2A 适合长时间运行、状态化、多轮委派的协调场景。
6. 未来工作：探索动态、LLM 驱动的协调结构（运行时合成/调整，而非先验固定）。

## 7. 优点

- **真实实现对比**：而非纯规范级讨论，给出可运行、可复现的 MCP/A2A 双实现（含完整源代码）。
- **多语言、跨框架实现**：Java（语法监督智能体，绑定 Emfatic 解析器）+ Python（其余智能体，契合主流 LLM 框架），验证互操作性需求 $R_6$。
- **多维度需求评估**：从协议规范与实现两端，对 7 项工程相关需求进行系统比较。
- **诚实的研究边界声明**：作者明确将结论限定为"基于窄协调场景的设计观察"，而非普适结论。
- **理论与实践结合**：将当代 LLM 智能体协调问题置于经典 MAS 文献（artifacts、social semantics、environment as first-class abstraction）背景中讨论。
- **关注基础设施层替代方案**：指出可借助 MCP 资源/工具暴露 mailbox、task queue 等共享通信构件，为后续工作指明方向。

## 8. 不足与局限

- **场景范围狭窄**：仅评估一种固定的协调模式（生成—验证—细化循环），未涵盖动态、协商、竞争、层级、市场等更广泛的 MAS 协调模式。
- **样本规模有限**：30 条 prompt 不构成统计意义上的 benchmark，且未报告独立运行的次数、随机种子、置信区间。
- **缺乏性能与成本基准**：未给出时延、token 消耗、吞吐量、错误率等量化指标；因此"MCP 更轻量"的结论主要基于 LOC、原语数等结构性指标。
- **定性评估主观性**：需求满足度（✓ / ∼ / ✗）依赖作者判断，未提供评分者一致性或多专家验证。
- **可观测性（$R_5$）在两个协议中均为部分满足**：作者未深入对比 Langfuse/Arize Phoenix 与两个协议的集成差异，super-task ID 问题未给出解决方案。
- **未来工作提及的"MCP 基础设施中介协调"（共享 mailbox/task queue 暴露为 MCP 资源）**：仅作为方向提及，未在本次实验中评估，可能存在遗漏的"中立"方案。
- **算力与工程细节不透明**：未披露 LLM 部署、GPU 配置、推理时长，影响复现与外推。
- **风险与偏差**：评估结果可能受作者使用的 `qwen2.5-coder:32b` 模型能力、以及 prompt 设计影响；Java/Python 双语言分工（受 Emfatic 解析器约束）可能放大 A2A 实现复杂度（任务/事件/产物管理显式编程）的相对观感。
- **协议版本依赖**：论文引用的 MCP、A2A 规范版本可能与撰写/审稿时不一致，比较结果对协议演化敏感。
