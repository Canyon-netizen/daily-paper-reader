## TLDR
跨平台GUI智能体面临高质量跨平台交互轨迹稀缺、不同平台交互约定差异导致联合或持续训练时出现行为模式混合与灾难性遗忘问题。为此构建了Uni-GUI统一跨平台数据集，并提出UI-MOPD方法，通过平台条件路由动态选择平台专属教师，将各平台行为先验迁移至共享策略。在OSWorld和MobileWorld基准上分别取得38.2%和12.0%的任务成功率，有效平衡了跨平台能力保留与新平台适配。

## Abstract
Recent advances in multimodal foundation models and agent systems have driven GUI agents from single-platform task execution toward cross-platform interaction. However, building multi-platform GUI agents remains challenging. On one hand, high-quality and executable cross-platform interaction trajectories are still scarce, and existing data often suffer from limited platform coverage. On the other hand, different platforms exhibit distinct interaction conventions, making joint or continual training prone to behavioral pattern mixing, platform-specific capability degradation, and catastrophic forgetting. To address these challenges, we construct Uni-GUI, a high-quality cross-platform GUI interaction dataset, and propose UI-MOPD, the first method that incorporates multi-teacher on-policy distillation into continual learning for GUI agents. UI-MOPD dynamically selects a platform-specific teacher according to the current environment and transfers platform-specific behavioral priors to a shared policy through platform-conditioned distillation, enabling adaptation to new platforms while preserving capabilities on existing ones. Experiments on OSWorld and MobileWorld show that UI-MOPD achieves task success rates of 38.2% and 12.0%, respectively, demonstrating its effectiveness in balancing cross-platform capability retention and new-platform adaptation. Project page: https://elispectre.github.io/UI-MOPD/.

## 结论
UI-MOPD是首个将多教师在策略蒸馏引入GUI智能体持续学习的方法，通过平台条件路由机制解决了跨平台行为模式混合与灾难性遗忘问题，为构建统一多平台GUI智能体提供了新路径。

## 一、全文翻译(节选)

近年来,多模态基础模型与智能体系统的进展推动了 GUI(图形用户界面)智能体从单平台任务执行迈向跨平台交互。然而,构建多平台 GUI 智能体仍面临挑战:一方面,高质量且可执行的跨平台交互轨迹仍然稀缺,现有数据往往存在平台覆盖有限的问题;另一方面,不同平台具有截然不同的交互约定,这使得联合训练或持续训练容易出现行为模式混合、平台特定能力退化以及灾难性遗忘。为应对这些挑战,我们构建了 Uni-GUI 这一高质量跨平台 GUI 交互数据集,并提出 UI-MOPD——首个将多教师在策略蒸馏引入 GUI 智能体持续学习的方法。UI-MOPD 根据当前环境动态选择平台专属教师,通过平台条件蒸馏将平台特定行为先验迁移至共享策略,使模型在适配新平台的同时保留已有平台能力。在 OSWorld 与 MobileWorld 基准上的实验表明,UI-MOPD 分别取得 38.2% 和 12.0% 的任务成功率,验证了其在跨平台能力保留与新平台适配之间的有效平衡。

## 二、研究背景与动机

随着多模态基础模型与智能体系统的快速发展,GUI 智能体已成为连接模型智能与真实数字环境的关键载体。早期 GUI 智能体研究主要集中在 Web 导航、桌面操作系统自动化、移动应用控制等单平台场景,代表性基准如 OSWorld、MobileWorld 推动了从静态界面理解向长时程、平台原生交互的转变。然而,真实工作流往往跨越桌面应用、移动 App 与 Web 服务,需要智能体在异构 GUI 环境间持续适配,同时保留各平台特有的交互约定。

现有跨平台 GUI 智能体的两条主流路线——混合 SFT / 混合 RL 与模型合并(Model Merge)——都存在显著缺陷。前者将异构平台的监督信号聚合到同一损失中,容易产生"过度平均化"策略,抹平平台专属交互语义;后者在参数空间静态合并,虽能保留部分通用能力,但容易丢失平台特定行为模式,在持续学习场景下还会引发灾难性遗忘。本文的中心问题由此提出:如何在共享一个 GUI 智能体策略的前提下,既能在异构平台间持续适配,又能保留各平台独特的交互行为?

这一问题背后有两个核心瓶颈:(1)高质量跨平台交互轨迹稀缺,现有数据集多为单平台,且常含无效动作、状态-动作错位、任务粒度不一致等问题;(2)桌面与移动平台的动作语义和可操作性差异巨大(例如"返回"在桌面可能是关闭窗口、在移动端则是按返回键),简单混合会破坏平台行为锚点。

## 三、方法详解

### 3.1 整体框架

UI-MOPD 的训练流程分为两阶段。第一阶段为平台特定 SFT:在 Uni-GUI 上分别对 Qwen3-VL-32B-Thinking 做监督微调,得到桌面教师 π_d^ref 与移动教师 π_m^ref。第二阶段为多教师在策略蒸馏(MOPD)持续学习阶段:将 Qwen3-VL-8B-Thinking 初始化为学生策略 π_θ,在强化学习过程中,学生先按当前策略在线采样来自两个平台的 rollout,再根据 rollout 的平台标签,通过平台条件路由器(Platform Router)动态选取对应平台教师,对该轨迹上 token 级分布施加反向 KL 惩罚;同时叠加规则化 ORM 提供的序列级奖励。整个目标函数为 PPO/GRPO 风格裁剪目标与多教师蒸馏 KL 项的加权和。

### 3.2 关键模块

**多教师在策略蒸馏(MOPD)**:区别于离线从静态轨迹蒸馏或直接 logits 合并,MOPD 让学生策略从自身当前分布在线采样轨迹,仅在学生实际访问的状态上施加教师约束,KL 信号聚焦于学生"真正犯错"的位置,避免学生被迫模仿教师所有行为模式。蒸馏信号按平台分桶处理——来自桌面的 rollout 对齐桌面教师,来自移动的 rollout 对齐移动教师,异构信号不会塌缩为单一约束。

**平台条件教师路由(Platform-Conditioned Teacher Routing)**:由于桌面与移动平台在视觉布局、动作语义、可操作性结构与执行上下文上存在根本差异(桌面依赖鼠标、键盘快捷键、滚动与窗口切换,移动端依赖点击、滑动、长按与 App 导航),单一教师或 logits 混合会压平异构行为。UI-MOPD 显式记录每条 rollout 的平台源标签 s_i,通过公式 π_ref^(i) = π_m^ref (若 s_i ∈ S_mobile) 或 π_d^ref (若 s_i ∈ S_desktop) 进行路由。该路由仅影响教师对数概率计算,学生仍是单一共享策略,推理阶段不增加额外教师开销。

**自适应 KL 掩码**:当某一 prompt group 的平均奖励已足够高(>τ_KL)时,任务反馈足以驱动策略改进,此时过强的 KL 正则会限制探索,因此将该组的教师惩罚关闭;仅在低奖励组上保留教师指导。该机制让蒸馏信号"集中在策略最需要的地方"。

### 3.3 关键公式解读

$$\mathcal{L}_{\text{MOPD}}(\theta) = \frac{\sum_{i \in \mathcal{B}} \sum_t m_t^{(i)} \mu^{(i)} \hat{D}_{\text{KL}}^{(t,i)}}{\sum_{i \in \mathcal{B}} \sum_t m_t^{(i)} \mu^{(i)}}$$

符号含义:m_t^(i) 为 prompt / padding 掩码;μ^(i) 为自适应 KL 掩码(奖励高时置 0、低时置 1);D̂_KL^(t,i) 为 token 级 KL 估计。整体为带掩码的 token 级 KL 加权平均。

$$\hat{D}_{\text{KL}}^{(t,i)} = \rho_t^{(i)} - \delta_t^{(i)} - 1, \quad \text{其中} \ \delta_t^{(i)} = \log \pi_{\text{ref}}^{(i)}(y_t \mid h_t^{(i)}) - \log \pi_\theta(y_t \mid h_t^{(i)}), \quad \rho_t^{(i)} = \exp(\delta_t^{(i)})$$

符号含义:K3 无偏 KL 估计器,只需学生与教师在采样 token 上的对数概率之差 δ 与 exp(δ),避免对完整词表求 KL,实现低成本且低方差。h_t^(i) 为解码状态,x^(i) 与 y_<t^(i) 的拼接。

$$\mathcal{J}(\theta) = \mathbb{E}_{p, x, y \sim \pi_\theta}\left[\sum_t m_t\left(\ell_t^{\text{PG}}(\theta) - \beta \mu \hat{D}_{\text{KL}}^{(t,p)}\right)\right]$$

符号含义:整体训练目标最大化;第一项 ℓ_t^PG(θ) 为 GRPO 风格裁剪策略梯度项(min(r_t A_t, clip(r_t,1-ε_low,1+ε_high)A_t)),第二项为路由到对应平台教师 p 后的 token 级 KL 惩罚;β 控制蒸馏强度,μ 为自适应掩码,A_t 为组内归一化优势。

### 3.4 图表解读

**图 1(三种集成策略对比)**:(a) 模型合并——在参数空间对桌面与移动教师做加权平均,易导致交互约定塌缩;(b) 混合 SFT——在动作空间混合两个平台的监督信号,导致桌面动作与移动动作语义冲突;(c) 本文 UI-MOPD——通过平台路由器按环境动态选择教师,通过 MOPD 把平台特定先验注入共享策略,实现平台感知的多模式激活。

**图 2(整体训练 pipeline)**:左侧 Stage-1 展示从 Uni-GUI 统一数据采集 Harness 出发,分别对桌面与移动数据做 SFT 得到两类平台教师;右侧 Stage-2 展示学生在线 rollout → ORM 规则化评估 → 平台路由器选择教师 → 在采样 token 上计算 token 级 KL 惩罚 → 与序列级奖励共同构成正则化策略优化目标的全流程。

**图 3(移动案例)**:展示 UI-MOPD 在邮件撰写并附加附件任务中,能正确理解指令"回复关于希腊菜 Moussaka 的评论内容应为 'Nice sharing, i love it'",从 Recent 文件列表中识别 waiver.jpg 并点击附加,完成多步结构化 chain-of-thought 推理与可执行动作序列。

## 四、实验设置与结果

### 4.1 数据集与基线

**训练数据**:Uni-GUI 包含约 11.5K 条高质量跨平台交互轨迹,合计约 160K 步(桌面自采集 95K + OpenCUA 13K;移动自采集 17K + OpenMobile 35K)。数据经统一 Harness 四阶段处理(query 生成 → 轨迹采集 → 轨迹清洗 → 后处理),并以子任务级判定确保成功。

**评估基准**:OSWorld(桌面,361 任务)、MobileWorld(移动,117 任务),另含静态 GUI 评估 AndroidControl⋆(4,260 步级记录)、ScreenSpot-Pro、ScreenSpotV2、OSWorld-G。指标统一为任务成功率。

**基线方法**:分四组——通用模型(SeedVL-1.5、Qwen3-VL-8B/32B/235B-Instruct/Thinking)、单平台 GUI 模型(OpenCUA-7B/32B、OpenAI CUA o3)、多平台 GUI 模型(UI-TARS-72B-DPO、UI-TARS-1.5-7B、GELab-Zero-4B、GUI-Owl-7B/32B)、集成策略(Mixed-SFT、Model Merge 权重平均、TIES Merging)。

### 4.2 主要结果

UI-MOPD 在 OSWorld 上取得 38.2%、在 MobileWorld 上取得 12.0% 的任务成功率,均为对比方法中最优的平衡表现。相对 Qwen3-VL-8B-Thinking 基线(33.9% / 7.7%),OSWorld 相对提升 12.7%、MobileWorld 相对提升 55.8%。

值得关注的是,现有 GUI 基线大多"偏科":GELab-Zero-4B 在 MobileWorld 达 10.9% 但 OSWorld 仅 31.9%;GUI-Owl-7B 在 OSWorld 达 34.9% 但 MobileWorld 跌至 4.5%。而 Mixed-SFT 在 MobileWorld 仅 6.4%、Model Merge(TIES)在 MobileWorld 为 0%,说明静态合并与简单混合均不能有效跨平台。UI-MOPD 同时使用一个 8B 学生模型,即在更小模型上 MobileWorld 仍超过了 32B 基线 Qwen3-VL-32B-Thinking(9.4%)。

### 4.3 消融实验

**教师-学生能力迁移分析(Table 2)**:(1)平台特定 SFT 会导致不平衡——8B 模型在 OSWorld 数据上 SFT 后,桌面升至 35.8% 但移动跌至 0%;在 MobileWorld 数据上 SFT 后,移动升至 12.8% 但桌面仅 35.8%。说明单平台监督会让模型偏向一种交互风格而牺牲跨平台鲁棒性。(2)UI-MOPD 在 OSWorld 与 MobileWorld 上同时获得 +4.3 点提升,说明平台条件蒸馏确实让共享策略同时受益。(3)32B 教师提供更强单平台参考(OSWorld 46.3%、MobileWorld 16.2%),学生只需从中蒸馏部分平台特定行为知识即可,无需部署多个教师。

**静态 GUI 与 grounding 评估(Table 3 / Table 7)**:在 AndroidControl⋆ 上 UI-MOPD 将总体准确率从 78.73% 提升至 80.05%,而 Model Merge(TIES)降至 74.01%;ScreenSpot-Pro 与 ScreenSpotV2 上 UI-MOPD 保持与基线接近(43.14% vs 43.71%、90.88% vs 91.27%),Model Merge 则显著退化(37.13% / 88.60%);OSWorld-G 上 UI-MOPD 反超基线(52.84% vs 52.13%)。这表明 UI-MOPD 在跨平台交互提升的同时,对通用 GUI grounding 与视觉理解能力的破坏远小于静态参数合并。

## 五、Related Work 与本文定位

GUI 智能体研究从单平台(Web 导航、桌面 OS 自动化、移动 App 控制)逐步走向多平台,代表工作包括 UI-TARS-2、UI-Venus-1.5、MobileAgent-v3.5 等多平台 GUI 智能体。这些方法主要通过"更大规模数据 + 统一架构"实现跨平台泛化,但仍以"聚合更多数据"或"统一训练"为核心思路。

在策略蒸馏方向,单教师在策略蒸馏(OPD)与在策略自蒸馏(OPSD)已成为缓解后训练中"跷跷板效应"的成熟方案;多教师在策略蒸馏(MOPD)则在基础模型后训练中崭露头角,MiMo-V2-Flash、GLM-5、Nemotron-Cascade 2、DeepSeek-V4 等均使用 MOPD 整合多个专家模型。然而,MOPD 在 GUI 智能体领域仍是空白。

UI-MOPD 的定位是首个把 MOPD 引入 GUI 智能体持续学习的工作,并创新性地提出"平台条件蒸馏"框架:教师不再按"能力维度"选取,而是按"环境来源"动态路由,使每个平台都有专属的行为锚点,从而避免异构交互信号在同一 KL 约束下被压平。这一思想与传统的混合 SFT、模型合并有本质区别——它把"跨平台异质性"作为建模对象而非噪声。

## 六、优点与局限性

**优点**:
1. **首次将 MOPD 引入 GUI 智能体持续学习**:方法论新颖,平台条件教师路由机制巧妙地把"环境异质性"转化为"教师选择条件",而非用单一教师或 logits 混合强行融合异构信号。
2. **数据 + 方法双轮驱动**:Uni-GUI 数据集提供约 11.5K 高质量跨平台轨迹,统一 Harness 解决了跨平台数据格式与动作空间对齐问题;UI-MOPD 在此基础上进一步蒸馏,数据-方法形成闭环。
3. **跨平台能力保留与新平台适配的良好平衡**:在 OSWorld 与 MobileWorld 上同时取得最优,且在静态 GUI grounding 评估上几乎不损失甚至略有提升,优于 Model Merge 的明显退化。

**局限性**:
1. **教师规模远大于学生(32B → 8B)**:教师-学生规模差距显著,蒸馏过程可能丢失部分细粒度平台知识,导致 MobileWorld 绝对成功率仍偏低(12.0%)。
2. **平台扩展性受限**:当前框架仅支持桌面与移动两类教师路由,扩展到 Web、IoT、车载等更多平台时,路由空间会指数增长,且自适应 KL 阈值 τ_KL 等超参需要重新调优。
3. **奖励设计粒度有限**:结构化 outcome reward 依赖规则化维度匹配,对于长时程任务中"过程对、结果错"或"过程错、结果对"的情况区分度有限,可能影响 GRPO 优势估计的信号质量。

## 七、复现要点

**代码与数据**:论文标注 GitHub、Hugging Face 与 Homepage 链接开源,Uni-GUI 数据集已公开。训练使用 verl 框架,Megatron-Core 作为训练后端,SGLang 作为 rollout 引擎,推理使用 vLLM。

**核心超参**:学生 Qwen3-VL-8B-Thinking 初始化,教师 Qwen3-VL-32B-Thinking 经 SFT 得到;两阶段各训练 1 epoch;训练 batch size 128、generation batch size 384、micro batch size per GPU 4;学习率 1×10⁻⁶,bfloat16 精度;每 prompt 采样 8 条 rollout;PPO 裁剪 0.2 / 0.28、C=10.0;K3 KL 损失系数 β=0.01;最大 prompt 长度 8192、最大 response 长度 512;温度与 top-p 均为 1.0;GPU 显存利用率 0.60;异步 rollout,最大并发序列数 1024。

**硬件需求**:64 张 NVIDIA H100 GPU,8 节点 × 8 卡;学生 8B 采用 TP=2 / PP=1 / DP=32,教师 32B 采用 TP=8 / DP=8;桌面图像分辨率 1920×1080,移动 1080×2400,训练时仅使用当前截图,推理时使用 4 张历史截图 + 当前截图 + 完整文本动作历史。

## 八、适用场景与延伸思考

**适用场景**:UI-MOPD 特别适合需要覆盖多个 GUI 平台(桌面、移动、Web)的企业级 AI 助手、个人效率工具、RPA(机器人流程自动化)系统,以及需要在不同终端设备间保持一致交互能力的智能客服与运维 Agent。同时,其平台条件教师路由思路可推广至"环境异质"的多任务持续学习场景,如多语言、多机器人形态、多软件栈的具身智能体。

**下游任务借鉴**:(1)将平台路由机制推广到 Web 平台,扩展为三平台甚至多平台 GUI 智能体;(2)把"平台"概念抽象为"任务域",用于多任务 RL 中缓解任务间干扰与灾难性遗忘;(3)借鉴 Uni-GUI 的统一 Harness 思想,构建跨模态、跨设备的高质量交互数据集;(4)将该框架应用于 GUI grounding 与 vision-language navigation 等需要多源异构监督的任务。

**未来工作方向**:(1)探索更高效的教师压缩与知识蒸馏(如 student 同规模甚至更大),提升绝对性能;(2)研究平台数量增多时的路由机制设计,如层次化路由器或基于 embedding 的软路由;(3)引入过程奖励模型(PRM)或偏好奖励,弥补当前 outcome reward 对长时程过程信号建模不足;(4)将 UI-MOPD 扩展到动态环境(应用更新、UI 变化)下的在线持续学习,真正实现"边用边学"的 GUI 智能体。
